# 启动延迟诊断与 V5.4.1 实机反馈

状态：已完成只读排查与结果记录；用户确认连续脉冲可用。每次启动的震感延迟仍存在，未声称已消除。

## 结论

- 用户确认“脉冲已经可以了”；快速拖动时仅震动没跟上，数值正常。因此本轮保留已有效的脉冲实现。
- 当前 WebKit CheckboxInputType.cpp 在原生 switch 的 touchstart 中设定 switchHeldDelay = 200 ms；计时完成才开始原生 pointer tracking，touchend／touchcancel 会停止未完成计时。与用户“每次启动都有延迟、快速划过无震动”的描述一致；这是源码依据，不是该两台手机的实测延迟。
- 页面的 changeTab 有 180／300 ms 视觉过渡，开始交互会取消过渡；没有按页签重新加载触感引擎，也没有“切换后等待”的新增触感计时器。通用触感请求有 55 ms 节流；它不等于 WebKit 的 200 ms 原生识别等待。
- 当前纯网页原生 switch 方案无法通过预加载或调大脉冲频率保证触下立即震动，也无法保证小于识别窗口的快速划动产生脉冲。即时马达控制需具备原生触感接口的应用环境，超出本次网页修正范围。

## 放大检查

当前放大样式及按下状态没有删除。Chrome 能力模拟在 390×844 和 420×890 下，色盘／材质盘／明度区域长按仍达到 1.24 倍；色盘白点 1.8 倍、明度白点 1.3 倍。

同时在 393×715 的较短视口发现：面板空间不足，prepareControlLift 的 verticalLimit 将整块控件限制为 1 倍，白点仍放大。截图还能看到面板内容下缘被裁切。因此不能把所有“看不到放大”都归因于触感等待；这是独立的短屏幕布局边界，本轮没有擅自改变面板高度或杯子构图。

浏览器首次采样 25 ms 时缩放尚为 1，约 95 ms 时较高视口已在放大，约 445 ms 时达到目标值。这是浏览器模拟的观察，不是实际 iPhone 的启动时间。Browser plugin not available；使用既有 Playwright／Chrome，无新增依赖。
